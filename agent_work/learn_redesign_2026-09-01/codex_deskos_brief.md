# Brief for Codex: Desk OS dashboard UI

Paste this whole thing to Codex as its starting context.

## What this is

MindCraft is a real, live ed-tech product (joinmindcraft.com marketing
site, a React app at mindcraft-93858.web.app, a Vercel-hosted API
backend). "Desk OS" is one surface inside it: a separate, static
HTML/CSS/JS single-page app (no build step of its own, no framework,
no bundler) that serves as the student's home dashboard after they log
in. It is NOT part of the React app's component tree; it is a
standalone static site that gets copied into the React app's public
folder and served alongside it.

You are being asked to redesign the visual UI of the Desk OS dashboard
specifically — the "Workspace" home screen the student lands on. Not
the marketing site, not the React app's other pages, not the backend.

## Where the files actually live (read this carefully, it is easy to get wrong)

- **Source of truth**: `agent_work/product/desk_os/` at the repo root.
  Edit files here. `index.html`, `styles.css`, and `js/*.js` are the
  real files.
- **Built copy**: `app/public/desk-os/` and `app/dist/desk-os/`. These
  are auto-generated by a sync script (`app/scripts/syncDeskOs.mjs`)
  every time the app builds. **Never edit these directly** — anything
  you change there gets silently overwritten and thrown away on the
  next build. If you find yourself editing a file under `app/public`
  or `app/dist`, stop, you're in the wrong copy.

## How this gets from your edit to a live URL

From the repo root:

```
cd app
npm run build
```

This runs `scripts/syncDeskOs.mjs` (copies `agent_work/product/desk_os/`
into `app/public/desk-os/`, stripping `node_modules`, `tests`, and
`*.md` files), then does the normal Vite build into `app/dist/`.

Then, from the repo root:

```
firebase deploy --only hosting:app
```

This deploys to the real production Firebase Hosting target. It will
almost always print an `HTTP Error: 400 ... supplied version is the
current active version` error at the very end — **this is a known,
harmless false failure**, not a real deploy failure. Verify the deploy
actually worked with a direct check instead of trusting that error
message:

```
curl -sL "https://mindcraft-93858.web.app/desk-os/" | grep -o 'something-you-just-changed'
```

If your change shows up in that curl output, it's live. Do this every
time, don't skip it.

The live URL for the page you're editing is:
`https://mindcraft-93858.web.app/desk-os/` (also reachable at
`joinmindcraft.com`'s app subdomain in some contexts, but the URL
above is the one to test against directly).

## How to preview locally before deploying

```
cd agent_work/product/desk_os
python3 -m http.server 8899
```

Then open `http://localhost:8899/index.html?mcEmail=test@example.com&mcName=Test&mcRole=student`
in a browser. The `mcEmail`/`mcName`/`mcRole` query params are a real,
intentional local-testing mechanism already built into this app
(`app.js`'s `readAuthHandoff()`) — Desk OS trusts these as an
"already authenticated" signal without needing real Firebase login,
specifically so it can be tested standalone. Use `mcRole=tutor` to
preview the tutor-role variant of the dashboard (it's a materially
different layout, tutors see three tool tiles instead of the student
Workspace view — check both).

## The real product surfaces this dashboard has to connect to

The dashboard is not just decoration. It has three real destinations,
wired through `js/bootHub.js` and `js/app.js`:

1. **The cube** (currently `.hub-orb-hero` / `[data-hub-mastery-nav]`)
   — clicking it navigates the browser away entirely, to `/learn`
   (the React app's real lesson/search experience). This is a full
   page navigation, not an in-page panel, because Desk OS and the
   React app are separate deployments.
2. **Tutors & events** (`[data-hub-jesse-nav]`) — opens an in-page
   panel (`#hubTutorMap`, driven by `js/tutorMap.js`) with a real map,
   real tutor listings, and a real event-posting flow backed by
   Firestore.
3. **Resume studio** (`[data-hub-resume-nav]`) — opens an in-page
   panel (`#hubResume`, driven by `js/resumeHelper.js`), a real chat
   interface (Jesse) that builds a resume draft, searches for real job
   openings via a backend API, and can generate a real PDF resume and
   cover letter.

None of that backend logic needs to change. You're building the visual
shell and wiring your new UI elements to these exact existing
functions (`onResumeOpen`/`onMapOpen` callbacks in `bootHub.js`, or the
`data-hub-*-nav` attributes directly), not rebuilding the features
themselves.

## Design language already established elsewhere in the product (match it, don't invent a new one)

- **Forest green + lime accent** is the brand pairing used everywhere
  else in this product right now (the marketing site's nav, the
  Learn page's retheme, the ZPD graph). Roughly: deep forest green
  (`#12251c`–`#1d3a2b` range) for primary UI chrome/buttons, a bright
  lime-green (`#c4f547` range) as the punchy accent, warm cream/off-white
  backgrounds (`#fdfbf5`–`#f6f4ec` range), not stark white.
- The brand mark is a raccoon (`img/orbs/raccoon-logo.png` inside this
  folder), and "Jesse" the owl is the tutor/assistant persona
  throughout the product, referenced by name in chat UI.
- Serif display font (Fraunces or similar) for large headings,
  sans-serif for body text — check `styles.css`'s existing font-family
  declarations near the top for the exact stack in use.
- **Hard rule, no exceptions: never use an em dash or en dash anywhere.**
  Not in UI copy, not in code comments, not in commit messages. This
  applies to everything you write. Use a period, comma, or "and"
  instead.

## What NOT to do

- Don't touch `app/public/desk-os/` or `app/dist/desk-os/` directly
  (see above, gets overwritten).
- Don't touch anything under `webhook/` (the backend) unless a UI
  change genuinely requires a new field from an existing endpoint,
  and even then, ask first rather than assuming.
- Don't remove or rename the `data-hub-*` attributes/IDs that
  `js/bootHub.js` and `js/app.js` query for (`[data-hub-mastery-nav]`,
  `[data-hub-jesse-nav]`, `[data-hub-resume-nav]`,
  `[data-hub-tutor-tiles]`, etc.) without updating the matching
  JS query alongside it, or the click handlers silently stop firing.
- Don't invent new Firebase/Firestore reads. If you want to show real
  student data (name, progress, activity), the existing pattern is
  `bootHub.js`'s `setUser()`/`paintJesse()` functions reading from a
  `users/{uid}` doc already fetched elsewhere in `app.js` — ask for
  the exact shape of that data before assuming a field exists.

## What's actually being asked for

The founder wants a genuinely better visual design for the dashboard's
home ("Workspace") view: a real tab row for navigating between
Workspace / Resume studio / Tutors & events, and a strong, polished
visual centerpiece (the current build uses a CSS 3D cube with a canvas-
drawn particle/constellation texture on its faces, which did not land
well). Bring real design thinking, reference the brand language above,
and check in with a screenshot before doing a full implementation pass
if you're proposing a substantially different visual direction than
"cube."

## How to verify before calling it done

1. `cd app && npx tsc --noEmit` should still pass (Desk OS itself has
   no TypeScript, but the sync script runs as part of the same build,
   so a broken sync breaks the whole app build).
2. `npm run build` completes with no errors.
3. Local preview (see above) at both a normal desktop width and a
   narrow mobile width (~400px), and both `mcRole=student` and
   `mcRole=tutor`.
4. Deploy, then verify live with curl (see above), don't trust the
   deploy command's own success/failure message.
