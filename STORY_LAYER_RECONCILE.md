**Author:** Opus (architect). **Implements:** almost nothing — this is mostly a

## The finding

The rulebook specs three separate things for a served practice question:

| Rulebook § | Spec'd endpoint | Reality |
|---|---|---|
| 1.2 | `/story-agent` — narrative wrap + scene descriptor | **Never built as spec'd.** Folded into `/story-module`. |
| 1.3 | `/question-frame` — stakes frame around a question | **Never built as spec'd.** Folded into `/story-module`. |
| 5.4 | Image gen (Flux/DALL-E), keyed `{concept}_{hash(student)}` | **Built differently:** per-*concept*, offline, checked in. |

What actually ships:

- **Themed stems (baked)** — `app/src/data/themedStems.generated.json`, produced
  offline by `webhook/scripts/bake-themed-stems.ts` using the shared composer in
  `webhook/lib/storyModuleComposer.ts`. Keyed `{conceptId}__{questionId}`.
  Practice serve order: **baked > framedLocalStem > plain**. Revises the earlier
  "text via LIVE `/story-module`" decision in this doc — see
  `THEMED_QUESTION_BAKE_BUILD.md`.
- **`/story-module`** (`webhook/api/story-module.ts`) — optional **live overlay**
  (llama-3.3-70b) returning per question: `storyStem` + `socratic[]` (2) +
  `steps[]` (2–5) + optional `misconceptionCallout`. Practice uses the overlay
  for guidance only; base stem comes from the bake. Cached per
  `{concept, question}` in Firestore (`story_module_cache`, 30-day TTL). Hard
  numeric-preservation validation drops any item that mutates the math.
- **`storyArt`** (`app/src/lib/storyArt.ts`) — art resolved **per concept**,
  generated **offline** by `app/scripts/generateConceptArt.mjs` (Higgsfield)
  + hand-authored SVGs, checked into `assets/canvas/generated/`,
  auto-discovered by glob. Precedence: generated jpg/svg > hand-picked ART map
  > theme fallback. Always returns a real image. This is §5.4 done as a
  rerunnable offline pipeline, not a live per-question call.

## The design decision (ratify what shipped)

**Art is keyed per CONCEPT, generated offline. Do not move to per-question live
image generation.**

**Themed STEM text is also offline-baked** (same discipline as art) —
deterministic per `{concept, question}`. Live `/story-module` remains only for
optional non-deterministic overlay (socratic / steps / goals). See
`THEMED_QUESTION_BAKE_BUILD.md`.

Rationale:
- The image sets the **world** (a property of the concept). `/story-module`'s
  text sets the **scene within that world** (per question). Together that's a
  bespoke-feeling question without a bespoke image.
- Per-concept = ~42 images, generated once, ~$0 at runtime, no session latency.
- Per-question live = ~1,500 images (one per bank question), paid image API,
  generated mid-session on first serve. ~35× the asset cost and a latency hit
  for marginal gain.
- Text personalization already covers the per-question delta; the graph's
  weakness ranking already covers *which* question. The image doesn't need to.

**Escalation path (only if a product reason appears):** if a specific concept
genuinely needs per-question art, generate it offline into the same
`assets/canvas/generated/` glob keyed by a `story-{conceptId}-{qId}` filename —
`storyArt` already picks the most-specific asset. This stays offline and cached;
it never becomes a live per-serve call. No runtime architecture change.

### `/story-module` contract (documents the shipped code)

**Input:**
```json
{
  "conceptId": "...", "conceptName": "...", "story": "<=4000 chars",
  "questions": [{ "id", "question", "choices", "correctIndex",
                  "explanation", "hints?", "level?", "format?",
                  "misconceptionLabel?", "conceptStory?", "protagonist?",
                  "storyContext?", "storyIntro?" }],
  "goals?": { "tags": [], "text": "" },
  "tutorFocusConcepts?": [], "priorOutcomes?": [], "sessionKind?": "practice"
}
```
Max 12 questions/call. Auth: Firebase ID token (same as other data endpoints).

**Output:**
```json
{ "items": { "<questionId>": { "storyStem", "socratic": ["",""],
             "steps": ["",""], "misconceptionCallout?" } },
  "cached": <n>, "generated": <n> }
```

**Invariants (already enforced in code — keep them):**
- LLM never touches math: choices, `correctIndex`, every digit-run preserved
  verbatim; items failing validation are dropped, not served.
- No answer leakage in `socratic`/`steps`.
- No em dashes (voice rule). No script/markup injection.
- Cache per `{concept, question}`; only misses hit Groq, in one batch call.
- On Groq failure: return cache hits; client renders plain questions for the
  rest. Never blocks the session.

## What Cursor actually has to build

Runtime stem path is implemented in `THEMED_QUESTION_BAKE_BUILD.md`
(composer extract + bake script + Practice baked-first). Remaining ops:
- Re-run `npm run bake-themed-stems --prefix webhook` after bank
  changes; use `-- --coverage-only` to flag gaps.
- (Optional) confirm `GROQ_API_KEY` is set on Vercel so the **guidance overlay**
  still works; stems no longer depend on it.
- (Optional, only if per-concept art coverage has gaps) rerun
  `generateConceptArt.mjs` for uncovered concepts — offline, not a code change.

Do **not** build a live `/story-question` endpoint that fuses text + image at
serve time. That was the earlier idea; reading the code showed it would regress
the offline/cached architecture already in place.
